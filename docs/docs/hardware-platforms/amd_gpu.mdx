This document describes how to run SGLang on AMD GPUs. If you encounter issues or have questions, please [open an issue](https://github.com/sgl-project/sglang/issues).

## System Configuration

When using AMD GPUs (such as MI300X), certain system-level optimizations help ensure stable performance. Here we take MI300X as an example. AMD provides official documentation for MI300X optimization and system tuning:

- [AMD MI300X Tuning Guides](https://rocm.docs.amd.com/en/latest/how-to/tuning-guides/mi300x/index.html)
- [LLM inference performance validation on AMD Instinct MI300X](https://rocm.docs.amd.com/en/latest/how-to/rocm-for-ai/inference/vllm-benchmark.html)
- [AMD Instinct MI300X System Optimization](https://rocm.docs.amd.com/en/latest/how-to/system-optimization/mi300x.html)
- [AMD Instinct MI300X Workload Optimization](https://rocm.docs.amd.com/en/latest/how-to/rocm-for-ai/inference-optimization/workload.html)
- [Supercharge DeepSeek-R1 Inference on AMD Instinct MI300X](https://rocm.blogs.amd.com/artificial-intelligence/DeepSeekR1-Part2/README.html)

**NOTE:** We strongly recommend reading these docs and guides entirely to fully utilize your system.

Below are a few key settings to confirm or enable for SGLang:

### Update GRUB Settings

In `/etc/default/grub`, append the following to `GRUB_CMDLINE_LINUX`:

```text GRUB Configuration
pci=realloc=off iommu=pt
```

Afterward, run `sudo update-grub` (or your distro’s equivalent) and reboot.

### Disable NUMA Auto-Balancing

```bash Disable NUMA
sudo sh -c 'echo 0 > /proc/sys/kernel/numa_balancing'
```

You can automate or verify this change using [this helpful script](https://github.com/ROCm/triton/blob/rocm_env/scripts/amd/env_check.sh).

Again, please go through the entire documentation to confirm your system is using the recommended configuration.

## Install SGLang

You can install SGLang using one of the methods below.

### Install from Source

```bash Command
# Use the last release branch
git clone -b v0.5.18 https://github.com/sgl-project/sglang.git
cd sglang

# Compile sgl-kernel
pip install --upgrade pip
cd python/sglang/kernels/aot
python setup_rocm.py install

# Install sglang python package along with diffusion support
cd ../../../..
rm -rf python/pyproject.toml && mv python/pyproject_other.toml python/pyproject.toml
pip install -e "python[all_hip]"
```

### Install Using Docker (Recommended)

The docker images are available on Docker Hub at [lmsysorg/sglang](https://hub.docker.com/r/lmsysorg/sglang/tags), built from [rocm.Dockerfile](https://github.com/sgl-project/sglang/tree/main/docker).

The steps below show how to build and use an image.

1. Build the docker image.
   If you use pre-built images, you can skip this step and replace `sglang_image` with the pre-built image names in the steps below.

   ```bash Command
   docker build -t sglang_image -f rocm.Dockerfile .
   ```

2. Create a convenient alias.

   ```bash Command
   alias drun='docker run -it --rm --network=host --privileged --device=/dev/kfd --device=/dev/dri \
       --ipc=host --shm-size 16G --group-add video --cap-add=SYS_PTRACE \
       --security-opt seccomp=unconfined \
       -v $HOME/dockerx:/dockerx \
       -v /data:/data'
   ```

   If you are using RDMA, please note that:
     - `--network host` and `--privileged` are required by RDMA. If you don't need RDMA, you can remove them.
     - You may need to set `NCCL_IB_GID_INDEX` if you are using RoCE, for example: `export NCCL_IB_GID_INDEX=3`.

3. Launch the server.

   **NOTE:** Replace `<secret>` below with your [huggingface hub token](https://huggingface.co/docs/hub/en/security-tokens).

   ```bash Command
   drun -p 30000:30000 \
       -v ~/.cache/huggingface:/root/.cache/huggingface \
       --env "HF_TOKEN=<secret>" \
       sglang_image \
       python3 -m sglang.launch_server \
       --model-path NousResearch/Meta-Llama-3.1-8B \
       --host 0.0.0.0 \
       --port 30000
   ```

4. To verify the utility, you can run a benchmark in another terminal or refer to [other docs](../basic_usage/openai_api_completions) to send requests to the engine.

   ```bash Command
   drun sglang_image \
       python3 -m sglang.bench_serving \
       --backend sglang \
       --dataset-name random \
       --num-prompts 4000 \
       --random-input 128 \
       --random-output 128
   ```

With your AMD system properly configured and SGLang installed, you can now fully leverage AMD hardware to power SGLang’s machine learning capabilities.

## Quantization on AMD GPUs

The [Quantization documentation](../advanced_features/quantization#platform-compatibility) has a full compatibility matrix. The short version: FP8, AWQ, MXFP4, W8A8, GPTQ, compressed-tensors, Quark, and **petit_nvfp4** (NVFP4 on ROCm via [Petit](https://github.com/causalflow-ai/petit-kernel)) all work on AMD. Methods that depend on Marlin or NVIDIA-specific kernels (`awq_marlin`, `gptq_marlin`, `gguf`, `modelopt_fp8`, `modelopt_fp4`) do not.

A few things to keep in mind:

- FP8 works via Aiter or Triton. Pre-quantized FP8 models like DeepSeek-V3/R1 work out of the box.
- AWQ uses Triton dequantization kernels on AMD. The faster Marlin path is not available.
- MXFP4 requires CDNA3/CDNA4 and `SGLANG_USE_AITER=1`.
- `petit_nvfp4` enables NVFP4 models (e.g., [Llama 3.3 70B FP4](https://huggingface.co/nvidia/Llama-3.3-70B-Instruct-FP4)) on MI250/MI300X via [Petit](https://github.com/causalflow-ai/petit-kernel). Install with `pip install petit-kernel`; no `--quantization` flag needed when loading pre-quantized NVFP4 models.
- `quark_int4fp8_moe` is an AMD-only online quantization method for MoE models on CDNA3/CDNA4.

Several of these backends are accelerated by [Aiter](https://github.com/ROCm/aiter). Enable it with:

```bash Command
export SGLANG_USE_AITER=1
```

Example -- serving an AWQ model:

```bash Command
python3 -m sglang.launch_server \
    --model-path hugging-quants/Mixtral-8x7B-Instruct-v0.1-AWQ-INT4 \
    --trust-remote-code \
    --port 30000 --host 0.0.0.0
```

Example -- FP8 online quantization:

```bash Command
python3 -m sglang.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --quantization fp8 \
    --port 30000 --host 0.0.0.0
```

### MiniMax-M3 TP2 prefill on MI325X

For the MXFP8 checkpoint, the gfx942 path retains the existing block-FP8 conversion, FP8 GEMM inputs, and BF16 hidden states. With `SGLANG_USE_AITER=1`, selected dense projections use prefill tiles from 8,192 rows onward. The MI325X Triton 3.7.0 MoE configuration also tunes the 128-expert, 1,536-wide intermediate shape at that boundary; smaller batches retain the previous configuration. Neither optimization adds quantization or changes the sparse-attention calculation.

A local two-MI325X comparison used `--tp-size 2 --quantization mxfp8 --dtype bfloat16 --attention-backend triton --moe-runner-backend triton --kv-cache-dtype fp8_e4m3`, with `SGLANG_OPT_USE_BF16_ROUTER_GEMM=0`, `--chunked-prefill-size 8192`, and `--max-prefill-tokens 8192`. Prefix caching was disabled with `--disable-radix-cache`. The figures below are prompt tokens divided by mean time to first token, not decode throughput: one fixed token-ID workload resized to each length, concurrency one, 16 greedy output tokens, three timed repetitions after kernel warmup.

| Input tokens | Frozen-source baseline input tokens/s | Tuned input tokens/s | Throughput gain |
| --- | --- | --- | --- |
| 8,192 | 6,318 | 8,201 | 29.8% |
| 32,768 | 6,104 | 7,841 | 28.5% |

Dense and MoE numerical probes preserved BF16 outputs bit-for-bit, including dense graph replay; the compared requests produced identical text and reported zero cached tokens. This is not a replacement for a full model-quality evaluation. Increasing both prefill limits to 32,768 yielded only another 2.5% on the 32,768-token workload and 1.4% at 131,072 tokens, so the 8,192-token scheduling recommendation remains unchanged.

These measurements do **not** establish 20,000 input tokens/s. In the optimized 8,192-token prefill trace, reductions consumed about 281 ms and sparse attention about 218 ms on one TP rank; those two current paths alone exceed the 410 ms total budget required for that rate. Unquantized quick-reduce did not improve large-message throughput, and the tested native MoE backend did not support the required clamped SwiGLU activation.

### MiniMax-M3 PP4 256K prefill on MI325X

Four MI325X GPUs reached the 20,000 aggregate input-token/s target for **eight simultaneous 262,144-token requests** with PP4 × TP1, FP8 attention, and 8,192-token prefill chunks. This measurement used the MXFP8 checkpoint, ROCm 7.2, PyTorch 2.9.1, and Triton 3.7.0. Each request generated one token; throughput is 2,097,152 input tokens divided by elapsed time through the last request's first token, not per-request throughput or decode speed.

| Configuration | Time through last first token | Aggregate input tokens/s |
| --- | --- | --- |
| Frozen-source PP4 baseline, 15/15/15/15 layers | 252.69 s | 8,299 |
| Tuned FP8, 3/19/19/19 layers, run 1 | 103.73 s | 20,217 |
| Tuned FP8, 3/19/19/19 layers, run 2 | 103.72 s | 20,219 |
| Tuned FP8, 3/19/19/19 layers, run 3 | 103.77 s | 20,211 |

All timed runs reported zero cached tokens and zero retractions. Compilation/autotuning warmup was excluded; the first, profiled warmup took 117.99 seconds. Warm the full prefill workload before relying on these figures. The slowest timed run has only about 1% headroom over the target; different prompts, cold starts, or concurrent decode need separate measurements.

The first three model layers use full attention rather than sparse attention. Giving them their own pipeline stage avoids the severe imbalance of an even 15-layer partition at long contexts. The remaining stages each run 19 sparse layers. Tuned TP1 dense projections, routed-expert tiles, full-attention query tiles, and sparse-prefill occupancy reduce computation on those stages.

The measured launch uses:

```bash Command
HIP_VISIBLE_DEVICES=0,1,2,3 \
CUDA_VISIBLE_DEVICES=0,1,2,3 \
SGLANG_USE_AITER=1 \
SGLANG_ENABLE_M3_ROCM_FP8_ATTN_GEMM=1 \
SGLANG_DISABLE_M3_FP8_ATTN_GEMM=0 \
SGLANG_PP_LAYER_PARTITION=3,19,19,19 \
SGLANG_OPT_USE_BF16_ROUTER_GEMM=0 \
ROCM_QUICK_REDUCE_QUANTIZATION=NONE \
python3 -m sglang.launch_server \
    --model-path /workspace/models/MiniMax-M3-MXFP8 \
    --trust-remote-code \
    --tp-size 1 --pp-size 4 --disable-overlap-schedule \
    --quantization mxfp8 --dtype bfloat16 \
    --attention-backend triton --moe-runner-backend triton \
    --kv-cache-dtype fp8_e4m3 \
    --mem-fraction-static 0.92 --context-length 1048576 \
    --max-running-requests 64 --cuda-graph-max-bs-decode 64 \
    --chunked-prefill-size 8192 --max-prefill-tokens 8192 \
    --max-total-tokens 2162688 --disable-radix-cache \
    --reasoning-parser auto --tool-call-parser auto \
    --model-loader-extra-config '{"enable_multithread_load":true}' \
    --random-seed 288168147 --watchdog-timeout 3600 \
    --host 127.0.0.1 --port 30110
```

The explicit cache capacity exceeds the eight prompts' combined 2,097,152 tokens. The ROCm FP8 attention setting is opt-in and requires gfx942, the Triton backend, and an e4m3 KV cache. It uses native `float8_e4m3fnuz` queries and main/index caches while retaining BF16 hidden states and attention outputs. `SGLANG_DISABLE_M3_FP8_ATTN_GEMM=1` takes precedence and restores BF16 sparse queries/index caches.

FP8 indexing can change selected sparse blocks; this mode is **not** bitwise equivalent to BF16 attention. Native FP8 prefill/decode passed kernel-reference, ragged-prefix, scaling, sink, and noncontiguous-slot checks, and the server passed a short arithmetic chat smoke. These checks are not a full model-quality evaluation; validate task accuracy before deployment.

### Kimi-K3 on gfx942

For `moonshotai/Kimi-K3` on MI300X/MI325X, this fork retains packed MXFP4 expert weights and uses BF16 matrix instructions rather than native FP4 instructions. The validated base-model configuration uses eight MI325X GPUs with `--tp-size 8`, ROCm 7.2, PyTorch 2.9.1, and Triton 3.6.0. Set `SGLANG_USE_AITER=1`, `SGLANG_AITER_K3_OPT=1`, and `SGLANG_AITER_MXFP4_TRITON=1`.

The gfx942 path avoids expert sorting for single-token MoE execution and uses K3 TP8 stage-specific tiles, including a K512 gate tile for single-token decode. The compatibility MoE runner writes directly into a caller-published output buffer when available, avoiding a separate output copy. ROCm MLA also skips redundant multiplication of BF16 weights by a scalar unit scale. For eligible small-batch, 512-dimensional MLA decode, the split merge runs across parallel value tiles with FP32 accumulation; larger batches retain the serial merge.

For covered K3 routing shapes, radix-4 expert selection is enabled automatically on gfx942 at batch sizes 1–64. It preserves AITER's ordered expert IDs, bias conversion, and winner-order normalization, including NaN weights on complete sigmoid underflow. Set `SGLANG_K3_RADIX4_TOPK=0` to retain AITER routing, or `=1` to request radix-4 for all supported shapes up to 1024 tokens. Unsupported shapes and hardware continue through AITER.

Long-prefill execution bounds routed activation workspaces to 2 GiB while retaining the full-batch GEMM configuration and top-k reduction order. Residual-bank addressing uses 64-bit offsets for banks larger than 2³¹ elements. Eligible single-sequence, zero-prefix MHA prefills of at least 32,768 tokens use the measured gfx942 K3 tile geometry.

Set `SGLANG_MLA_DECODE_TUNE=1` to enable the K3 TP8 C4 decode schedule on gfx942. It retains N16 probability rounding and the scheduler's split counts; C1 retains its existing launch. In a same-process, shared-weight comparison against tuning off, all 384 sampled GSM8K/MMLU outputs and four supplementary 120,000-token retrieval/arithmetic outputs had identical generated token sequences and token logprobs. This finite check isolates the C4 schedule, not speculative decoding or all prior optimizations. The setting is opt-in; very short C4 sequences can be slower.

These optimizations do not require speculative decoding or change the checkpoint, activation precision, or KV-cache format. The parallel merge changes FP32 summation order, so do not assume bitwise-identical generation. Validate task accuracy against your baseline before deployment.

#### Kimi-K3 DFlash2 on MI325X

The selector-equipped [`lightseekorg/kimi-k3-dflash2`](https://huggingface.co/lightseekorg/kimi-k3-dflash2) checkpoint uses MLA, not the GQA architecture of plain Kimi DFlash drafts. This fork supports its compressed MLA KV cache, grouped convolutions, candidate selector, and completed-layer prefix captures. Select it with `DFLASH`; there is no `DFLASH2` algorithm flag.

Download the reviewed draft before an offline launch:

```bash Command
hf download lightseekorg/kimi-k3-dflash2 \
    --revision e77935fb4804e17eb55085bffd045eae1d779769 \
    --local-dir /workspace/models/Kimi-K3-DFlash2
```

For TP8 on MI325X with the target already in `/workspace/models/Kimi-K3`, this configuration favors uncached long-prefill latency:

```bash Command
SGLANG_USE_AITER=1 \
SGLANG_AITER_K3_OPT=1 \
SGLANG_AITER_MXFP4_TRITON=1 \
ROCM_QUICK_REDUCE_QUANTIZATION=NONE \
HF_HUB_OFFLINE=1 \
python3 -m sglang.launch_server \
    --model-path /workspace/models/Kimi-K3 \
    --trust-remote-code \
    --tp-size 8 \
    --dtype bfloat16 \
    --kv-cache-dtype fp8_e4m3 \
    --attention-backend triton \
    --mem-fraction-static 0.85 \
    --max-total-tokens 524288 \
    --chunked-prefill-size 120000 \
    --max-prefill-tokens 120000 \
    --max-running-requests 64 \
    --cuda-graph-max-bs-decode 8 \
    --disable-radix-cache \
    --speculative-algorithm DFLASH \
    --speculative-draft-model-path /workspace/models/Kimi-K3-DFlash2 \
    --speculative-dflash-block-size 8 \
    --speculative-draft-attention-backend triton \
    --speculative-draft-kv-cache-dtype bfloat16 \
    --linear-attn-prefill-backend triton \
    --linear-attn-decode-backend triton \
    --linear-attn-verify-backend triton \
    --enable-linear-replayssm-spec \
    --linear-replayssm-cache-len 16 \
    --mamba-ssm-dtype float32 \
    --reasoning-parser kimi_k3 \
    --tool-call-parser kimi_k3 \
    --model-loader-extra-config '{"enable_multithread_load":true}' \
    --random-seed 288168147 \
    --watchdog-timeout 1200 \
    --host 0.0.0.0 --port 30000
```

Keep PP at one and DP-attention off. The MLA draft currently requires unquantized weights and the Triton attention backend; the target retains its MXFP4 expert weights. Do not set a global `--speculative-draft-window-size 4096`: four draft layers have trained sliding windows, but the fifth needs full context. An absent draft `aux_hidden_stream` selects the publisher's `prefix` serving convention; explicit `attn_res` is also supported without changing the completed-layer IDs. Legacy DSpark keeps its AttnRes convention.

The 120,000-token outer prefill uses the zero-prefix MHA path rather than repeatedly traversing compressed prefixes through absorbed MLA. Large single-sequence BF16 KDA prefills with indexed FP32 state bound their internal workspaces to roughly 32K-token slices, merging short tails to retain the kernel schedule. A 120K isolated comparison saved 2.24 GiB with bitwise-identical outputs and final FP32 state. Target auxiliary features are packed directly into their final buffer, and MoE front activations are released before the full-width tail allocations.

This is a memory-capacity tradeoff: resident target KV capacity is 524,288 tokens rather than the measured automatic allocation of 728,798. Graph capture stops at batch eight rather than 64; the 64-request admission limit is unchanged, but larger decode batches use eager execution. Four concurrent 120K prompts completed without retractions. Weight/cache dtypes, FP32 recurrent state, model context length, and the draft's trained windows are unchanged. For the earlier higher-residency configuration, use `--chunked-prefill-size 32768 --cuda-graph-max-bs-decode 64` and omit `--max-total-tokens`. Neither setting truncates requests.

On the fixed 120K-token retrieval prompt at C1, three final uncached streaming runs measured 17.29–17.50 s to first token (17.43 s mean), versus 24.99–25.14 s (25.09 s mean) with the earlier 32K-chunk configuration. Effective input throughput rose from 4,783 to 6,884 tokens/s: 30.5% lower TTFT and 43.9% higher effective prefill throughput. Generated token IDs matched on every timed run. A one-rank profile reduced target prefill attention from 96 launches / 10.79 s to 24 launches / 3.72 s; MoE tile and RCCL channel sweeps did not produce a consistent improvement and were not adopted.

Three repeated 1K-input/8K-output C1 checks retained 198.31–198.39 tokens/s over the post-first-token decode window (198.35 mean versus 198.71 previously, a 0.18% decrease), with identical generated texts. These fixed-prompt measurements are not a general throughput guarantee.

A fresh paired 384-item comparison matched every generated token sequence and all 11,310 evaluated token logprobs exactly, with unchanged 124/128 GSM8K and 230/256 MMLU scores. All four 120K retrieval/arithmetic controls passed at both C1 and C4; all eight token sequences matched the earlier chunked controls. Long-context arithmetic is not bitwise equivalent: the 382 compared output logprobs differed by 0.0070 nats on average in absolute value, with a 0.1917-nat maximum. These finite controls do not establish a global quality-loss bound. The no-prefix-cache setting reproduces this validation configuration.

The initial 384-item greedy quality comparison had no regressed answers: both non-speculative and native DFlash2 runs scored 124/128 on GSM8K and 230/256 on MMLU. Teacher-forced logprobs matched, but only 343/384 free-generation token sequences were identical. This finite sample does not establish a global quality-loss bound. Speculation uses target verification rather than ordinary decode, so the C4 `SGLANG_MLA_DECODE_TUNE` schedule above does not accelerate its target path.

On gfx942, eligible eight-token MLA verification batches at concurrency one through four automatically partition the 512 value channels into independent 128-channel tiles. This retains the original query tile, serial KV traversal, and arithmetic precision; it does not split or reorder the softmax reduction. No additional flag is needed.

A fresh paired comparison of this optimization against unmodified DFlash2 matched all 384 free-generation token sequences and all 11,310 evaluated token logprobs exactly, with unchanged GSM8K and MMLU scores. An untouched-source restart itself changed correctness on two GSM8K items relative to the earlier warm server (one regression and one improvement); that pre-existing restart discrepancy remains unexplained.

Three consecutive 1,000-input/8,000-output streaming requests at concurrency one measured 198.64–198.77 tokens/s over the post-first-token decode window: a mean of 198.71 versus 167.92 for the fresh unmodified control, an 18.3% improvement. End-to-end output throughput was 197.30–197.41 tokens/s, with 229.6–233.8 ms to first token. All three generated texts matched the control. These repeated fixed-prompt runs used temperature zero, seed 42, and ignored EOS to force the requested output length; they are not a 200 tokens/s guarantee or a natural-generation quality test.

#### Furnace image builds

The Furnace GHCR release job looks for a successful scheduled AITER nightly at the exact reviewed source revision, built with the matching Python 3.10, Torch 2.9.1, ROCm 7.2, and gfx942/gfx950 recipe. It verifies the upstream artifact SHA256 before accepting its wheel. Verified downloads are cached by source revision, ABI, and reuse policy; misses are not cached, so later builds retry when the nightly becomes available. Arbitrary `latest` wheels are not interchangeable: the per-commit staging channel can use a different Torch ABI. Custom base images and LLVM builds stay source-only.

Only native HIP modules are reused, not upstream Python files or Triton/FlyDSL compiler caches. The Dockerfile's patched DSv4 rotate/quant module is excluded and compiled from source when needed. Unknown source, shared-header, build-recipe, or submodule changes disable reuse of all native modules. Apply upstream source patches before the seeding step; AITER's native cache is name-addressed, so editing a running installation does not automatically invalidate its binaries.

If no compatible artifact is available, the release job installs the pinned AITER source with `PREBUILD_KERNELS=0` and builds/import-checks its core without requiring a GPU. Other modules compile on first use. This avoids the exhaustive build-all pass, but **first model startup can still spend time compiling the kernels it needs**. The image retains the compiler and source required for that path.

Fork-local AOT kernels remain source-built in a separate cacheable layer before the full repository copy. Python or documentation changes can reuse that layer; AOT source, header, packaging, and compiler-flag changes invalidate it. Furnace's separate JIT kernels retain their source-aware caches, so prebuilt AITER modules do not override local kernel modifications. Downloaded wheel archives are build inputs only and are not retained in the final image.

For an explicitly source-only build, pass `--build-arg AITER_USE_PREBUILT=0 --build-arg AITER_PREBUILD_KERNELS=0`. To restore exhaustive AITER compilation, use `AITER_USE_PREBUILT=0` with `AITER_PREBUILD_KERNELS=1`. Other ROCm image flavors keep their previous build policy unless these arguments are supplied.

### Warmup Step

When the server displays `The server is fired up and ready to roll!`, it means the startup is successful.
